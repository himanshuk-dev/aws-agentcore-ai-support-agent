## Reflection

This project demonstrated how an AI support agent becomes more reliable when model reasoning is separated from authoritative operations. I used AgentCore Gateway with MCP for order and refund tools because operational data should come from backend systems rather than from the model's generated knowledge. The same principle guided the Knowledge Base integration: product policies and loyalty benefits are retrieved through RAG, while AgentCore Memory is used only for customer context and preferences. Code Interpreter provides an isolated execution path for deterministic loyalty calculations, and Browser adds access to live web content.

The most significant implementation challenge appeared after the agent had already deployed successfully. A fresh Runtime invocation worked, but a subsequent invocation in the same Runtime session could fail inside Starlette and AnyIO while handling AgentCore's synchronous **/ping** route. I isolated the problem by inspecting the installed AgentCore routes, dependency versions, and Python compatibility metadata. The application was using Python 3.14, while the installed **bedrock-agentcore** release explicitly classified support through Python 3.13. I moved the project and container to Python 3.13 without simultaneously changing the core AgentCore/Starlette/AnyIO stack. All 27 tests and 68 subtests passed, and repeated deployed invocations then succeeded.

For production, security and observability would be priorities. Refund operations should use authorization and idempotency controls, Memory should follow strict privacy and retention rules, and IAM permissions should remain least-privilege. I would also monitor tool latency, failures, retrieval quality, model hallucinations, token cost, and cross-customer memory isolation.
